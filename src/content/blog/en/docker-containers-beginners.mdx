When I first encountered Docker in 2019, I spent three weeks confused about what it actually did. The documentation talked about "containerization," "images," and "layers," but none of it clicked until I built something real. Since then, I have onboarded approximately 30 junior developers to Docker across three companies. The approach in this guide is what consistently works.

This is not a reference manual. It is a learning path that takes you from zero to running a containerized application with confidence.

## What Docker Actually Does (In Plain English)

Before Docker, deploying applications was painful. Your code worked on your laptop but failed on the server because the server had a different version of Node.js, missing system libraries, or conflicting dependencies with other applications.

Docker solves this by packaging your application with everything it needs to run — code, runtime, system tools, libraries, and settings — into a single unit called a container. This container runs identically on your laptop, a test server, and production.

Think of it like shipping a complete, self-sufficient appliance rather than a list of parts and instructions. The recipient does not need to know how to assemble anything. They just plug it in.

## Your First Container

Install Docker Desktop from docker.com. Once installed, open a terminal and run:

```bash
docker run hello-world
```

This downloads a minimal image and runs it. The output explains what Docker just did: it checked locally for the image, downloaded it from Docker Hub since it was not found, and ran the container. This single command demonstrates the entire Docker workflow.

### Understanding What Happened

Three concepts are at work here:
1. **Image**: A read-only template with instructions for creating a container. The `hello-world` image contains a tiny program that prints a message.
2. **Container**: A runnable instance of an image. When you ran `docker run`, Docker created a container from the `hello-world` image.
3. **Docker Hub**: A registry where images are stored and shared. When the image was not found locally, Docker pulled it from Hub.

## Building Your Own Image

Running existing images is useful, but the real power comes from building your own. Create a new directory and add two files.

`app.py`:
```python
from flask import Flask
app = Flask(__name__)

@app.route('/')
def hello():
    return "Hello from Docker!"

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

`Dockerfile`:
```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
```

`requirements.txt`:
```
flask==3.0.0
```

Build the image:
```bash
docker build -t my-first-app .
```

The `-t` flag tags the image with a name. The `.` tells Docker to look for a Dockerfile in the current directory. You will see output showing each step of the build process. Notice how Docker caches layers — if you rebuild without changing `requirements.txt`, the `pip install` step is skipped because it is already cached.

Run your container:
```bash
docker run -p 5000:5000 my-first-app
```

The `-p 5000:5000` maps port 5000 on your host to port 5000 in the container. Visit `http://localhost:5000` and you will see your application running.

## Essential Commands You Will Use Daily

| Command | Purpose |
|---|---|
| `docker ps` | List running containers |
| `docker ps -a` | List all containers (including stopped) |
| `docker images` | List local images |
| `docker stop <id>` | Stop a running container |
| `docker rm <id>` | Remove a stopped container |
| `docker rmi <id>` | Remove an image |
| `docker logs <id>` | View container output |
| `docker exec -it <id> /bin/sh` | Open a shell inside a running container |

The `docker exec` command is particularly useful for debugging. When a container is not behaving as expected, opening a shell inside it lets you inspect the filesystem, check environment variables, and run diagnostic commands.

## Volumes: Persisting Data

Containers are ephemeral by design. When a container stops, any data written inside it disappears. This is a feature, not a bug — it ensures consistency and reproducibility. But most applications need persistent storage.

Docker solves this with volumes. A volume is a directory outside the container's filesystem that Docker manages. Create one:

```bash
docker volume create my-data
```

Run a container with the volume mounted:
```bash
docker run -v my-data:/data my-first-app
```

Now anything written to `/data` inside the container is persisted to the volume. Even if the container is removed and recreated, the data survives.

For development, I prefer bind mounts, which map a host directory directly into the container:
```bash
docker run -v $(pwd):/app my-first-app
```

This lets you edit code on your host and see changes immediately inside the container without rebuilding the image.

## Docker Compose: Multi-Container Applications

Real applications rarely consist of a single container. A typical web application needs an application server, a database, and possibly a cache or message queue. Managing these manually with `docker run` commands becomes unwieldy.

Docker Compose defines multi-container applications in a YAML file. Here is a realistic example for a Flask application with PostgreSQL:

`docker-compose.yml`:
```yaml
version: '3.8'

services:
  web:
    build: .
    ports:
      - "5000:5000"
    volumes:
      - .:/app
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
    depends_on:
      - db

  db:
    image: postgres:15-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=mydb

volumes:
  postgres_data:
```

Start everything:
```bash
docker-compose up
```

This builds the web service from your Dockerfile, pulls the PostgreSQL image, creates a network connecting the services, and starts everything. The `depends_on` ensures the database starts before the web application.

## Common Beginner Mistakes

After teaching Docker repeatedly, I see the same mistakes:

**Running as root inside containers.** By default, containers run as root. If an attacker compromises your application, they have root access inside the container. Fix this by creating a non-root user in your Dockerfile:
```dockerfile
RUN useradd -m myuser
USER myuser
```

**Bloated images.** Using `python:latest` or `ubuntu:latest` as your base image includes hundreds of megabytes of packages your application does not need. Use slim or alpine variants. The `python:3.11-slim` image is 45MB versus 900MB for the full image.

**Hardcoding configuration.** Never put database credentials, API keys, or environment-specific settings in your Dockerfile. Use environment variables that are injected at runtime. This makes the same image runnable in development, staging, and production.

**Ignoring .dockerignore.** Without a `.dockerignore` file, Docker copies your entire project directory into the build context, including `node_modules`, `.git`, and local configuration files. This slows builds and can accidentally include sensitive data.

## Moving Toward Production

For production deployments, additional considerations matter:

**Health checks** tell Docker whether your application is actually working, not just running:
```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:5000/health || exit 1
```

**Resource limits** prevent a single container from consuming all host resources:
```bash
docker run -m 512m --cpus=1.0 my-first-app
```

**Logging strategy:** Docker captures stdout/stderr by default, but for production, configure a logging driver that sends logs to a centralized system like CloudWatch or Splunk.

**Orchestration:** For multiple hosts, you need Kubernetes or Docker Swarm. These are advanced topics, but understanding Docker fundamentals first makes the transition significantly easier.

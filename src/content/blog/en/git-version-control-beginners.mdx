Git is the most powerful tool most developers use daily — and the one they understand least. In code reviews, I regularly see commit histories that tell no coherent story, merge commits that obscure what changed, and branch strategies that create more problems than they solve.

After onboarding approximately 20 junior developers to Git across three companies, I have refined a learning progression that builds genuine understanding rather than memorized commands. This guide follows that progression, from your first commit to confident collaboration.

## Understanding What Git Actually Does

Before running commands, understand the model. Git is not a backup system or a file sync tool. It is a content-addressable filesystem that tracks snapshots of your project over time.

### The Four Areas

Git manages files in four distinct areas:
1. **Working directory**: Your actual files on disk
2. **Staging area (index)**: Files marked for the next commit
3. **Local repository**: Committed snapshots on your machine
4. **Remote repository**: Committed snapshots on a server (GitHub, GitLab, etc.)

Understanding this flow is essential. When you edit a file, you are in the working directory. `git add` moves changes to staging. `git commit` saves the staged snapshot to your local repository. `git push` uploads local commits to the remote.

### Why This Matters

New developers often think `git commit` saves changes to the server. It does not — it saves locally. They think `git push` is required after every commit. It is not — you can make dozens of local commits before pushing. Understanding the four areas eliminates these misconceptions.

## Your First Repository

Create a directory, initialize Git, and make your first commit:

```bash
mkdir my-project
cd my-project
git init
```

Git now tracks this directory. Create a file:

```bash
echo "Hello, Git!" > README.md
git add README.md
git commit -m "Initial commit: add README"
```

The `git add` stages the file. The `git commit` creates a permanent snapshot with your message. Check the status anytime with `git status`.

### Writing Good Commit Messages

Commit messages are not afterthoughts — they are documentation for your future self and teammates. A good commit message has:
- A subject line under 50 characters describing what changed
- A blank line
- A body explaining why the change was made (not just what)

Bad: `fix bug`
Good:
```
Fix race condition in user authentication

The token validation was checking expiration before verifying
the signature, allowing expired tokens with valid signatures
to pass validation. Reordered checks to verify signature
first, then expiration.
```

This level of detail seems excessive for small changes, but it pays dividends during debugging. When `git blame` shows this commit, the explanation is immediately clear.

## Branching: Working in Parallel

Branches allow multiple lines of development to proceed simultaneously. The default branch is typically `main` or `master`.

### Creating and Switching Branches

```bash
git branch feature-login      # Create branch
git checkout feature-login    # Switch to it
# Or in one command:
git checkout -b feature-login
```

Make changes, commit them, and the branch moves forward while `main` stays unchanged. This isolation prevents experimental work from destabilizing the production codebase.

### A Practical Branching Strategy

For small teams, I recommend a simple workflow:
- `main`: Always deployable production code
- `feature/*`: Individual features or bug fixes
- `hotfix/*`: Urgent production fixes

Create a feature branch from main, do your work, then merge back through a pull request. No direct commits to main.

## Merging: Combining Work

When your feature is complete, you need to combine it with main.

### Merge vs. Rebase

`git merge` creates a merge commit that preserves the exact history of both branches. This is honest but can create a messy commit graph.

`git rebase` replays your commits on top of the target branch, creating a linear history. This is cleaner but rewrites history, which can be dangerous on shared branches.

### My Recommendation

For feature branches that only you work on, rebase before merging:
```bash
git checkout feature-login
git rebase main
# Resolve any conflicts
git checkout main
git merge feature-login
```

For shared branches or when you are unsure, use merge. Preserving the true history is more valuable than a clean graph.

## Remote Repositories: Collaboration

Working alone, Git is useful. Working with a team, it is essential.

### Setting Up a Remote

```bash
git remote add origin https://github.com/username/repo.git
git push -u origin main
```

The `-u` flag sets upstream tracking, so future pushes can be just `git push`.

### The Daily Workflow

```bash
# Start of day: get latest changes
git pull

# Create feature branch
git checkout -b feature-search

# Work, commit, work, commit
git add .
git commit -m "Implement search API endpoint"

# Push branch to remote
git push -u origin feature-search

# Open pull request, get review, merge
# Then clean up
git checkout main
git pull
git branch -d feature-search
```

### Handling Conflicts

Conflicts occur when the same line is modified in both branches. Git cannot decide which version is correct — you must choose.

When a conflict occurs, Git marks the file:
```
<<<<<<< HEAD
console.log("Hello from main");
=======
console.log("Hello from feature");
>>>>>>> feature-search
```

Edit the file to keep the correct version, remove the markers, then:
```bash
git add <file>
git commit  # Git pre-fills a merge commit message
```

The key skill is not resolving the conflict mechanically — it is understanding why the conflict occurred and ensuring the resolution preserves both changes' intent.

## Advanced Commands Worth Learning Early

### git stash

When you need to switch branches but have uncommitted changes:
```bash
git stash push -m "WIP: search implementation"
git checkout main
# Do something on main
git checkout feature-search
git stash pop
```

### git log

The default `git log` is overwhelming. Configure a useful alias:
```bash
git config --global alias.lg "log --color --graph --pretty=format:'%Cred%h%Creset -%C(yellow)%d%Creset %s %Cgreen(%cr) %C(bold blue)<%an>%Creset' --abbrev-commit"
```

Now `git lg` shows a concise, colorized, graphical history.

### git bisect

When a bug appears but you do not know which commit introduced it:
```bash
git bisect start
git bisect bad          # Current version has bug
git bisect good v1.0    # Version 1.0 was fine
# Git checks out a commit in between
# Test, mark good or bad
# Repeat until Git identifies the first bad commit
```

This binary search can identify the problematic commit in a history of thousands in under 10 steps.

## Common Mistakes and Recovery

### Accidental Commit to Wrong Branch

```bash
git reset HEAD~1        # Undo last commit, keep changes
git checkout correct-branch
git add .
git commit -m "Original message"
```

### Pushed Sensitive Data

If you commit a password or API key:
1. Change the credential immediately (it is compromised)
2. Use `git filter-repo` or BFG Repo-Cleaner to remove it from history
3. Force push the cleaned history
4. Notify team members to rebase their branches

Never simply delete the file in a new commit — it remains in history and is discoverable.

### Broken Main Branch

If main becomes broken, do not panic:
```bash
git checkout main
git log --oneline -10   # Identify last good commit
git revert <bad-commit>  # Creates new commit undoing the bad one
# Or for immediate fix:
git reset --hard <last-good-commit>
git push --force        # Only if team agrees and coordinates
```

## Developing Git Intuition

The developers who master Git share one trait: they understand the underlying model, not just the commands. When something unexpected happens, they reason about the four areas and the commit graph rather than frantically trying commands from Stack Overflow.

Build this intuition by:
1. Drawing commit graphs for operations before executing them
2. Using `git log --graph` to visualize what happened
3. Practicing recovery operations in a test repository
4. Reading Pro Git (free online) for conceptual depth

Git has a learning curve, but the investment is among the highest-return in software development. A developer comfortable with Git collaborates more effectively, recovers from mistakes confidently, and maintains a clear project history that helps the entire team.
